Microsoft Zero Trust Workshop - DevSecOps | Microsoft Learn

DevSecOps integrates security into the people, processes, platforms, code, pipelines, and infrastructure used to build and deliver software. The DevSecOps workshop pillar helps organizations reduce implicit trust across the software development lifecycle by governing identities and repositories, securing code and dependencies, hardening CI/CD pipelines, and protecting the software supply chain.

The DevSecOps workshop pillar helps organizations identify security gaps and create a prioritized implementation roadmap across developer platforms, source code, pipelines, build infrastructure, deployment environments, and security operations.

The DevSecOps workshop pillar corresponds to the SAF Development Security discipline rather than to an SAF technology.

Why focus on DevSecOps?

Compromised developer accounts, exposed secrets, vulnerable dependencies, untrusted pipeline components, insecure build runners, and weak release controls can provide paths from source code to production. The DevSecOps Workshop applies the Zero Trust principles of verify explicitly, use least privilege, and assume breach throughout the software development lifecycle.

The expected output is an actionable backlog of DevSecOps projects prioritized into First, Then, and Next based on organizational risk, dependencies, implementation effort, developer impact, coverage, and readiness.

DevSecOps implementation areas

AreaDetails
Establish DevSecOps strategy, ownership, and governanceDefine accountable owners, operating responsibilities, security requirements, metrics, remediation service-level objectives, exception processes, maturity reviews, and compliance evidence across engineering and security teams.
Inventory and govern developer platforms and repositoriesDiscover source repositories, DevOps organizations, build infrastructure, accounts, privileged groups, and service connections across platforms. Assign ownership, establish secure defaults, and prioritize onboarding into governance and security tooling.
Secure developer identities and accessIntegrate supported developer platforms with Microsoft Entra ID, apply Conditional Access, govern privileged groups and administrative roles, use access reviews and time-bound access where appropriate, and maintain tested emergency-access procedures.
Protect credentials and workload identitiesDetect and block exposed secrets, eliminate plaintext credentials, rotate existing secrets, and migrate pipelines and applications toward managed identities or workload identity federation. Scope permissions to the minimum required resources and operations.
Establish repository and code-review protectionsApply organization-wide repository baselines, branch protections, CODEOWNERS or equivalent ownership controls, peer-review and approval requirements, protected environments, and controls for untrusted contributions and fork-based workflows.
Implement application security testingIntegrate static, dynamic, API, and organization-specific security testing into developer workflows and CI/CD. Tune findings, surface feedback in pull requests or work items, and use third-party tools where they provide necessary coverage.
Secure dependencies and open-source usageEnable dependency inventory, alerts, updates, and pull-request review. Govern approved packages and registries, assess software composition and license risks, and prioritize vulnerable dependencies based on severity, exploitability, reachability, and business impact.
Protect the software supply chainGenerate software bills of materials, establish artifact signing and build provenance, verify integrity at deployment boundaries, govern trusted publishing, use approved base images, and secure AI or machine-learning model artifacts where applicable.
Harden CI/CD pipelines and build infrastructureUse version-controlled pipeline definitions, pin third-party actions and tasks to trusted immutable references, protect reusable templates, apply least privilege, use ephemeral or hardened runners where appropriate, and evaluate pipeline risks against recognized practices such as the OWASP CI/CD Top 10.
Secure infrastructure as code and deployment controlsScan infrastructure-as-code changes in pull requests and pipelines, define approved modules and security baselines, deploy policy as code, monitor configuration drift, and require approvals and security gates for protected environments and releases.
Protect containers and cloud-native deliveryScan container images in pipelines and registries, govern approved base images, sign and verify images where appropriate, protect registries and clusters, and integrate runtime container protection with build and deployment controls.
Manage findings, vulnerabilities, and remediationCreate a unified triage process for code, secret, dependency, pipeline, infrastructure, and cloud findings. Assign owners, apply risk-based remediation timelines, manage exceptions, clear existing backlogs, and track progress through centralized dashboards.
Integrate DevSecOps signals into security operationsConnect developer platforms and cloud security services to centralized monitoring and SIEM workflows. Establish code-to-cloud traceability, attack-path analysis, DevOps-specific incident-response playbooks, and coordinated vulnerability-disclosure processes.
Build secure engineering practices and cultureEmbed security requirements in backlogs and design reviews, establish threat modeling, provide role-based secure-development training, support security champions, govern AI-assisted development tools and data handling, and continuously improve using measurable outcomes.

These areas summarize the DevSecOps workshop pillar. Use the detailed DevSecOps project guidance to review individual projects and implementation considerations.

How to use the DevSecOps Workshop

Use the web-based Workshop with development, platform engineering, application security, cloud security, identity, infrastructure, data protection, compliance, and security operations stakeholders. For each relevant project:

  • Review the project objective and applicability to your environment.
  • Record the current status, notes, decisions, owners, and known dependencies.
  • Consider licensing, implementation effort, developer impact, technical prerequisites, coverage, and cross-pillar dependencies.
  • Prioritize the project into First, Then, or Next and incorporate it into the implementation roadmap.

Open the Zero Trust Workshop and select the DevSecOps pillar.

Review the detailed DevSecOps project guidance for project-level information.

Assess your DevSecOps posture

The Microsoft Zero Trust Assessment does not currently assess the DevSecOps pillar. Use the DevSecOps Workshop and detailed project guidance to evaluate your development platforms, repositories, pipelines, software supply chain, deployment controls, and operational processes. Findings from other assessed pillars can still provide useful cross-pillar context.

Learn about the Zero Trust Assessment and its current pillar coverage.

Who should participate?

  • Software engineering, application architecture, and engineering leadership teams.
  • Platform engineering, DevOps, site reliability engineering, cloud platform, and release-management teams.
  • Application security, product security, cloud security, identity, data protection, security operations, and incident response teams.
  • Governance, risk, compliance, legal, procurement, open-source program, and business or application owners. \ No newline at end of file
